What it does

One goal in plain English, four steps, then it repeats.

The agent decides what to call and when. Nothing below is scripted — the order emerges from the model reading your API's tool definitions.

01 · Design

Generate candidates

Mutates a starting binder into a batch of variants, each with an id.

02 · Pre-screen

Predict, for free

Scores every candidate on CPU and keeps only the promising ones. Cheap and imperfect — that's the point.

03 · Test

Order the assay

Prices it, asks before spending, then creates and submits the experiment.

04 · Learn

Use what came back

Measured winners become the parents of the next round. The loop closes.

Throughout this page, ochre marks a prediction and teal marks a measurement.

The idea it's built on

Pre-screening is the whole economic argument.

In your public EGFR competition, 601 of roughly 1,800 submitted designs were selected for wet-lab testing. Choosing which ones to test is the job. At $249 per sequence, testing 40 designs costs $9,960; testing the best 4 costs $996.

So the agent always predicts before it spends. But the prediction is deliberately an imperfect proxy for the measured result — because that is what protein design actually looks like. If prediction were reliable, the lab wouldn't be necessary and neither would the loop.

Integration with the Foundry API

I built the client against your OpenAPI schema, not your docs.

The schema is the contract. Your Python SDK isn't published to PyPI, so adaptyv_copilot/api.py talks to the REST API directly — bearer auth, the paginated list envelope, and errors surfaced with your request_id so they're traceable on your side.

Spending controls

An agent with a payment method needs a lock in code, not a polite prompt.

Ordering is blocked by default

Against the real Foundry, create and submit refuse unless ADAPTYV_ALLOW_ORDERING=true. The check runs before any HTTP request. Reads — targets, status, results, cost estimates — always work.

It confirms the amount first

The agent calls estimate_cost, states the dollar figure, and waits. A general “go ahead” earlier in the conversation is not treated as authorisation for a specific spend.

Nothing simulated is presented as real

The system prompt changes with the backend, and tool output carries a "source" field. A generated number is never described as a measurement — in the UI, the payload, or the agent's wording.

Both backends speak one vocabulary

I rebuilt the simulator to use your status enum, your seven assay types, your BLI/SPR requirement. A mock speaking a different dialect trains in bugs that only appear in production.

Architecture

What one message does.

1
app.py — Streamlit
Message appended to a plain list of dicts. That list is the conversation state.
2
brain.run_turn(...)
A generator. Yields events as they happen rather than returning a finished string, so the UI renders live and the same loop drives the CLI.
3
messages.create(model, system, tools, messages)
Backend-specific system prompt, 8 tool schemas, capped at 12 tool steps so it cannot spin.
4
tools.dispatch(ctx, name, input)
Every exception returns as {"error": …}. The model reads the error and corrects itself instead of the app crashing.
5
foundry.get_foundry(mode) → Simulated | Real
One interface, two implementations. The tool layer never knows which it holds.
6
api.AdaptyvClient → httpx → devs.adaptyvbio.com/api/v1
Real mode only.
7
result → tool_result → back to step 3
Appended as a user-role message; the loop runs again. That's the agent.

One decision worth calling out

The model never handles a protein sequence — only ids like cand_003. Real sequences stay server-side and are swapped back in at order time. Twenty-four 63-residue strings waste the context window, and models silently corrupt long strings when copying them. One wrong residue is a different protein and a wasted assay.

What I'd build next

In order.

  • Webhooks instead of polling. Your create endpoint already accepts a webhook_url and signs the body with HMAC-SHA256. The agent parks the campaign and the webhook wakes it when results land — that's what makes a three-week loop workable rather than theoretical.
  • A real structure predictor for the pre-screen. ESMFold or AlphaFold confidence in place of the biophysics heuristic. The scoring interface doesn't change.
  • A generative design model. ProteinMPNN or RFdiffusion output replacing the mutation generator.
  • Persistence. Campaign state in a database so a run survives a refresh. Correct for production, unnecessary for a demo.
  • The tool layer as an MCP server, so any assistant can order assays — not just this one.
